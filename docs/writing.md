# 文書の書き方(writing)

説明書・サイト・README に文を書くときの決まり。読む人は「mdgrid を使うかどうか決めたい人」と「もう使っていて、やり方を知りたい人」の2種類で、どちらも長い文章を読みに来ていない。

## 並べ方: 読む人の順に

1. 誰のための道具で、使うと何がどう見えるか(画面)。ここで「自分の場面だ」と思えなければ、先は読まれない。
2. 1分で試す道を1本だけ。前提と、できたと分かる目印(「この表が出れば成功」)を書く。
3. 自分の場面に当てはめる(タスク・読書・ブックマーク・人。スターターで作る)。
4. 作業の手引き(やりたいことから引く)。
5. 考え方(表・ビュー・ワークスペースの仕組み。手引きの途中で迷ったときに読む)。
6. 参照(キー・設定・安全)。網羅はここだけ。

上の6段は入口のページ(説明書の index とサイトの入口)の段落の順。説明書の章の並び(見せ方の一覧 → はじめかた → 手引き → 考え方 → 見た目 → 困ったとき → 参照)は SR-50 のとおりで、入口の段がそのまま章になる。入口のページは短く保つ。詳しさは下のページへ送る。機能を足したときは、入口に1行足すのでなく、該当する段に1項を足す(見せ方なら「見せ方の一覧」に、機能なら「できることの一覧」に、画面1枚と1項)。

これは Diátaxis(tutorial / how-to / explanation / reference)の分け方と同じで、入口と Getting started の次に手引きを置き、参照を最後に置く docs サイトの並びに合わせたもの。

## 文: 人が読んで温度のある文に

書いた文は、下の癖が無いかを読み直してから出す。AI の書いた文はこの癖で見分けられ、読む人に距離を感じさせる(Wikipedia の「Signs of AI writing」と、日本語の AI 文の癖の一覧から)。

- 具体から書く。「状況・困りごと・mdgrid でどうなるか」を場面で書き、抽象の説明は後ろに回す。例と画面を先に出す。
- 語尾と文の長さを変える。「〜ます。〜ます。〜ます。」と続けない。短い文と長い文を混ぜる。
- 接続詞を連ねない。「まず」「次に」「さらに」「しかし」で文を始め続けない。順を言いたいなら番号の一覧にする。
- 箇条書きは並列のものだけ。説明の段落を箇条書きに砕かない。1項が段落になる箇条書きは、段落に戻す。
- 大げさな語を使わない: 強力・シームレス・直感的・豊富・最適・〜を実現・〜の可能性を広げる・画期的・重要なポイント。何がどうなるかを書けば形容は要らない。
- 根拠の無い褒め言葉と、深そうで何も言っていない文を消す(「さまざまな場面で活用できます」)。根拠が書けないなら削る。
- 「〜ではなく〜です」「単なる〜ではありません」の対比の型と、三つ組の列挙(「速く、軽く、安全」)をくり返さない。
- 太字で強調しない(用語を初めて出すときの1回だけ)。見出しに記号や絵文字を付けない。
- 「〜することができます」は「〜できます」。「〜という形で」「〜において」「〜に関して」は、たいてい省ける。
- 締めの定型句(「いかがでしたか」「ぜひお試しください」「以上が〜です」)を書かない。説明が終わったら終わる。
- 「〜と言われています」「多くのユーザーが」のような出どころの無い言い方をしない。言うなら誰が・どこでを書く。
- 読む人に話しかける。「ユーザーは〜できます」でなく「〜できます」「〜を開くと」。
- 製品名で言い換えない(表の道具・ノートの道具と書く。`docs/design.md` の決まり)。

英語も同じ。delve・crucial・pivotal・seamless・robust・leverage・empower・showcase・a testament to・not only … but also・"it's important to note" を使わない。be 動詞を "serves as" で避けない。Title Case の見出しにしない。

## 書いたあと

1. 入口から順に、使ったことのない人のつもりで読む。3段落で「何が見えるか」が分かるか。
2. 上の癖の一覧に照らして、1つずつ直す。
3. 画面の画像は場面の台本(`docs/manual-scenarios.toml`)の id で指し、文に合う画面が無ければ場面を足す。
