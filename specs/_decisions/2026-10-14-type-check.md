# 型と決まりに合わない値を「問題」として探し、画面と CLI で確かめられるようにする(type-check)

## きっかけ

人が 2026-10-14 に、mdgrid に型のチェックの機能を付けてはどうかと言い、AI が示した3つの案(画面の中で不一致を探す・CLI で全体を確かめる・必須のキーと選べる値の決まりを設定に書く)を、3つとも合わせて実装すると決めた。人の依頼を AI が要件の文に起こした。今は表のセルの型と合わない値に `!` が付く(CV-2)だけで、見えていない行の不一致は探せず、CI でノートの形を守る手段も無い。キー・帯の出し方・CLI の出力の形・決まりの書き方は AI が置いた細部。

## 差分

- 追加: CE-36「表の列の決まりを、設定の `[rules.<列の名前>]` に `required`(真偽。真なら、キーが無い・null・空の文字列・空のリストを違反とする)と `values`(文字の配列。値の文字(リストなら各要素の文字)がこのどれかでなければ違反とする。大文字小文字を区別する)で書けるべきで、範囲ごとに項目ごとに重ね、狭い範囲が勝つべき(SR-44)。決まりはノートを書き換えず、決まりに合わない値を書くことも止めないべき(決まりは確かめるための物で、書いてから直す流れを妨げないため)。`values` のある列の編集では、CE-3 の数の上限によらず、その値を候補のリストに並べるべき。`file.*`・`formula.*` の列の決まりと、知らない項目・型の違う値は、警告してその項目を使わないべき。」(確かめ方: `[rules.status] required = true` と `values = ["todo", "doing", "done"]` → status の無いノートと `status: wip` のノートが違反(CV-9 の印)、`status: done` は違反でない。status のセルで Enter → 候補のリストに todo・doing・done。表の範囲で `values = ["todo", "done"]` を重ねる → 表では doing も違反。`[rules."file.name"] required = true` → 警告して使わない。`required = "yes"` → 警告(`test_ce_36_*`))
- 追加: CV-9「決まり(CE-36)に合わないセルにも、型と合わない値(CV-2)と同じ `!` の印を付けるべき(必須のキーが無いノートの空のセルにも付ける)。型と合わない値と決まりに合わない値を、画面と CLI でまとめて「問題」と呼び、理由を「型が合わない(日付ではない など)」「必須のキーが無い」「選べる値ではない」の3つで言い分けるべき。印は色だけに頼らない(SR-15)。」(確かめ方: `[rules.status] values = ["todo", "done"]` → `wip` のセルに `!`。`required = true` で status の無いノートの空欄に `!`。date の列の someday は今までどおり `!`(`test_cv_9_*`))
- 追加: NV-30「表のモードで、次の問題(CV-9)のセルへ跳ぶ操作(既定 `!`)と前の問題へ跳ぶ操作(既定 `g !`)があり(どちらも SR-4 のキーの表で割り当て直せ、パレットと操作の一覧からも使える)、表の行の順に(同じ行では列の順に)探して端で反対の端に回り、跳んだらメッセージ行にそのセルの問題の理由を出すべき。問題が無ければそう知らせて動かないべき。下の帯に、今の表(ビューの絞り込みのあとの行と、見えている列)の問題の数を、1つ以上あるときだけ出すべき(例「問題 3」)。問題のある行だけに絞る切り替えを、パレット・操作の一覧・下の帯の問題の数のクリックから使え、絞っている間はそれと分かるように出し、もう一度の切り替えで外せるべき。読むだけの起動(WB-15)でも使えるべき。」(確かめ方: 3つの問題のある表で `!` → 1つめの問題のセルに移り、メッセージ行に「due: 型が合わない(日付ではない)」。3回目の `!` のあと `!` → 1つめに戻る。`g !` → 前へ。下の帯に「問題 3」。パレットの「問題のある行だけ」→ 問題のある行だけ、もう一度 → 元に戻る。問題の無い表 → 帯に数が出ず、`!` で「問題は無い」(`test_nv_30_*`))
- 追加: CLI-22「`mdgrid [<.base | フォルダ> …] --check [--view <名前>]` は、画面を出さずに、開いたビュー(CLI-5 と同じく、ビューの絞り込みのあとの行。画面の見た目の状態は使わない)の各ノートの全部のフロントマターのキーと、決まり(CE-36)のある列を確かめ、問題(CV-9)を1つ1行で `<パス>:<行>: <列>: <理由>`(キーが無いときは行を付けず `<パス>: <列>: <理由>`)の形でパスと行の順に標準出力に出し、問題の数を標準エラーに1行で出すべき。列の型は CE-2 の順(設定・ルートフォルダの型の設定・確かめる行からの推定)で決めるべき。問題が無ければ終了コード 0、あれば 1、起動できないときは CLI-4 と同じく理由1行と 2 にするべき(CI と pre-commit で止められるようにするため)。パスは `--pick path`(OUT-3)と同じ形にし、ノートを書き換えないべき。」(確かめ方: `[types] due = "date"` で `due: someday` のノートと、`[rules.status] required = true` で status の無いノート → `notes/a.md:3: due: 型が合わない(日付ではない)` と `notes/b.md: status: 必須のキーが無い`、標準エラーに「問題 2」、終了コード 1。直したあと → 出力なし、終了コード 0。無いパス → 理由1行と終了コード 2(`test_cli_22_*`))

## 却下した案

| 案 | 理由 |
|---|---|
| 何もしない | 見えていない行の型の不一致を探せず、CI でノートの形を守る手段が無い |
| 決まりに合わない値を書かせない | 決まりは確かめるための物で、途中の値を書いてから直す流れを止める。型(CV-2)と違い、合わない値でも書き戻しの安全には関わらない |
| 決まりの違反を型と別の印にする | 印の種類が増えると読み分けが要る。印は同じ `!` にし、理由はメッセージ行と CLI で言い分ける |
| `mdgrid check` のようなサブコマンドにする | 今の CLI は `--print`・`--apply` のような旗でそろっているので、`--check` の旗にする |
| CLI でもビューの見えている列だけを確かめる | CI では表の全体を守りたい。画面は跳べる所(見えている列)だけを数え、CLI はノートの全部のキーを確かめる |
