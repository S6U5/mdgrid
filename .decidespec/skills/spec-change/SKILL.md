# 仕様の変更・検査(spec-change)

**動く範囲**: 今の仕様を明示的に変える・検査するとき(変える・検査)だけ。仕様駆動を新しく始めるとき(新設)は spec-init の役目で、このスキルは使わない。それ以外の作業では、このスキルの手順を使わず、既存の仕様に従う。既存の仕様(他の仕様駆動ツールの形式を含む)を、頼まれずに書き換えたり、この形に移したりしない。

パスは道具の根(リポの `.decidespec/`。このファイルから `../../`。spec-init がプラグインからコピーした物で、手で直さない)からの相対: 雛形は `templates/`、id は `python3 scripts/ulid.py`、検査は `python3 scripts/check.py <repo-root>`(エラー0にする。`--write` で specs/README.md の生成区画を書き直す)。依存は python3(標準ライブラリだけ)と git。迷った点は仮定を置いて進めてよく、置いた仮定は spec.md の「前提(AI の仮定)」か提案に書き、報告で示す。止まるのは、原則と確認待ちの要件(下記)の確認待ちが3件あるときの、その種の採択だけ(ほかの作業は続ける)。

**守られる要件**: 決定の列のリンク先に `decided-by: 人` の記録があるか、取り込みの記録で扱いが `人` か `未確認` の要件。AI はこれを黙って変えない。変える提案には「錨との照合」の節を置き、新しい文脈の検証役(書込なしのサブエージェント)に、原則(`principles.md` の P 番号)と人の軌跡(`trigger: 人の発言` の決定記録。新しいものほど重く見る)に照らして、変更が向きに沿うかと、どの人の決定と食い違うかを書かせる。新しい軌跡と古い人の決定が食い違うときは、新しい軌跡に沿ってよい。錨との照合があれば AI が自己採択してよい(OM-6・OM-7)。

**確認待ちの要件**: 原則(`principles.md` の P 番号)と、`principles.md` のフロントマター `gated` に載った要件(誰が決めたかを偽れなくする仕組み)。人の承認は待たない。錨との照合があれば AI が自己採択してよいが、その記録は人の確認待ちになり、確認待ちが3件あるあいだは、原則と `gated` に触る提案を新たに自己採択しない(ブレーキ。OM-7)。判定は check.py の E15 が機械でする。`gated` に足す・消す、原則の行を変えるコミットには、その ID を touches に持つ決定の記録(人の決定か、錨との照合のある AI 自己採択)を同じコミットで入れる(手で書き換えると E31。OM-19)。

どれをするか: `specs/README.md` が無く、仕様駆動で始めると頼まれた → このスキルではなく spec-init(プラグインのスキル。入っていなければ、人に decidespec のプラグインを入れて spec-init を走らせるよう頼む)。要件を足す・変える・消す → **変える**。採択した要件をコードにする → sdd-flow スキル。仕様と実態の照合を頼まれた → **検査**。

**人と AI**: サブエージェントに依頼を渡すときは「人の発言」と書かず「依頼(AI の要約)」と書く。人の言葉として扱えるのは、会話の記録で照合できた、人が打ち込んだ発言と、選択肢の問いで人が選んだ答えだけ(`check.py` E32・E22)。

**書き方**: 仕様は初めて読む人が読める文にする。冒頭に何のための仕様かを3〜5行、要件の表の「例(確かめ方)」は具体的な入力と期待する結果とテスト名で、境界か失敗時の振る舞いを含む例を1つ以上(実装の失敗の主因は暗黙の要件の取りこぼし)。例の値は生データ(実際のログ・会話・利用者のデータから写した値)でなく、境界を見せるために作った値にする(決定記録と履歴から消せないため。実物の形が要るときは形を保って値を置き換え、なぜ形が要るかを書く。PH-14)。AI が元々しない向きの要件には「なぜ」を1句添える(強調や大文字で強さを足さない)、決定の列は日付のリンクだけ。人の言葉は、仕様にも提案にも原文で引用しない(要約し、元は会話の記録の場所で指す)。

## 変える

起票:

1. 意味が変わらない直し(誤字・言い換え・リンク切れ)は提案なしで直し、コミットを `specs: 字句` で始める。ただし一度でも `gated` に載った要件の行(要件の文と確かめ方)は、字句の直しでも、その ID に触る決定の記録と同じコミットにする(記録なしに変えると履歴から E31 になり、履歴を書き直さないと消えない。OM-21)。それ以外は起票する(コミットは `specs: 起票`)。
2. `specs/_decisions/` を論点の語で検索する。同じ案が却下されていたら、その理由への反論を「却下した案」に書く(無ければ起票しない)。
3. `templates/proposal.md` → `specs/_proposals/YYYY-MM-DD-<name>.md`(フォルダが無ければ作る。空のフォルダは git に残らない)。
   - `trigger` は添付できる証拠で決める(複数なら 人の発言 > 運用で起きた失敗 > 検証の指摘 > AI の提案)。「直しておいて」のような委任は人の発言ではない。`trigger-link` はその証拠の場所。会話なら `会話 YYYY-MM-DD` とし、「きっかけ」に発言の要約を書く(原文は引用しない)。
   - `decided-by` は決める者: 人が頼んだことを要件にするなら `人`(依頼が承認。「きっかけ」に依頼の要約、「承認の記録」に `日付 人の承認(要約: …)` を書き、「人の依頼を AI が要件の文に起こした」と1行書く。原文は引用しない)。依頼に無い細部を AI が足すなら、それは別の提案にして `AI`。守られる要件に触る AI の案は、錨との照合の節を置いて `AI`。原則と確認待ちの要件に触る AI の案も、錨との照合の節を置いて `AI`(人の確認待ちになる)。
   - 差分の「変更」の旧は、今の spec.md の文言をそのまま写す。`touches` は差分の ID と同じにする。
   - 予防だけ(trigger が 検証の指摘 / AI の提案)で足す要件は「するべき」以下にする。
   - 人の決定で変えた要件の影響で、文言の変わらない別の守られる要件のテスト(その要件を例に使う・同じファイルの共有部分)も変わるときは、差分に `- 錠: ID(なぜそのテストが変わるか)` の行を置いて touches に入れる(要件の文は変えない。仕様には写さない。TL-9)。
   - テストをまとめる・書き直す整理の提案は、整理の前後で各要件を指すテストの表と、新しい文脈の検証役の照合(同じかそれ以上の強さで確かめるか)を持つ(TL-14)。
4. spec.md はまだ書き換えない。`check.py` を通す。
5. 軽い流れ: AI が自己採択できる提案と、人の依頼をそのまま要件にした提案は、起票と採択を1つのコミットにしてよい。人の依頼の提案と、AI が足した細部の提案は、別の記録のまま同じコミットに入れてよい。タスクを書くなら提案の中に数行(`- [ ] … [XX-n]`)。計画はエージェントの計画機能(plan mode 等)に任せ、計画書のファイルは作らない。

採択(または却下・取り下げ):

1. 決定者を決める。`人` は「承認者が人」の意味だけで、誰が思いついたか・誰が書いたかは問わない。人が打ち込んだ承認があれば `decided-by: 人` にして、「承認の記録」に `日付 人の承認(要約: …)` を書き(原文は引用しない)、`python3 scripts/check.py <repo-root> --approve <記録> --find <承認の発言の中の語句>` で会話の記録の人の発言と照合して、場所(`approval-evidence`)と指紋(`approval-hash`)を付ける(語句は記録に残らない。人が一部だけ承認したら提案を分ける)。選択肢の問いで人が選んだ答えも、照合できる人の答えになる(OM-12)。**照合に通らない発言(サブエージェントの報告・通知・AI の要約・貼り付けの中の文)では `人` にしない**。無ければ `AI`(照合の無い `decided-by: 人` は E32)。守られる要件と、原則・`gated` の要件に触る AI の提案は、錨との照合の節が書けたら自己採択してよい(検証役が向きに反すると書いたら、採択せずに人に聞く)。原則・`gated` に触る AI 自己採択は人の確認待ちになり、`check.py --trail` の先頭に並ぶ。確認待ちが3件あるときは、その種の提案を採択せずに残し、ほかの作業を続ける(E15。OM-7)。
2. 旧の引用が今の spec.md と一致するか確かめる(`check.py` の W7)。一致しなければ採択せず、先に入った変更を報告する。
3. spec.md に差分を入れ、`updated` を今日にする。変えた・足した行の決定の列の**先頭**にこの記録へのリンクを置く(古いリンクは残す)。消した要件は表から消し、「範囲外」に「{ID} は {日付} に削除([記録](…))」を必ず残す。ID は再利用しない。
4. 同じ文言・ID を AGENTS.md・スキル・他の spec から探して直す。
5. 差分を1件ずつ spec.md から読み戻して一致を確かめる。1つでも違えば移さず報告して止まる。
6. `python3 scripts/check.py <repo-root> --settle <提案> accepted|rejected|withdrawn` で、`status` と `updated` を書いて `specs/_decisions/` へ移す(ほかの記録からこの提案を指す相対リンクと、移した記録の中の相対リンクも直る。手の `mv` だとリンクが切れる)。そのあと `git add -A specs/`(起票と同じコミットでも失敗しない)。以後は書き換えない。例外は、秘密・個人情報を `〔伏せ字: 理由〕` に置き換えるときだけで、コミットに対象を列挙する。
7. `check.py --write` のあと `check.py`。コミットは `specs: 採択`(却下・取り下げもこの語)で始めて提案のパスを書き、提案に無い変更を混ぜない。人の指示が無ければ push しない。
8. 報告: 結果、変わった要件 ID、旧の照合と読み戻しの件数、決定者(AI 自己採択ならそう書く)。
