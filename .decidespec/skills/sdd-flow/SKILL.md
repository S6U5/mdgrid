# 仕様駆動の流れ(sdd-flow)

**動く範囲**: decidespec の形で仕様を持つリポで、コード(`specs/` の外の、Markdown でないファイル)を変える依頼のすべて(頼まれなくても使う)。仕様駆動のツールを何も使っていないリポでは、人が仕様駆動で進めるよう頼んだときだけ、spec-init で specs/ を作ってから使う。他の仕様駆動ツールの仕様を持つリポ(`.specify/`・`.kiro/`・`openspec/`・`.bmad-core/` など)では使わず、そのツールのやり方に従う。

パスは道具の根(リポの `.decidespec/`。このファイルから `../../`。spec-init がプラグインからコピーした物で、手で直さない)からの相対: 各フェーズの手順は `skills/sdd-flow/phases/`、記録の雛形は `templates/change.md`、検査は `python3 scripts/check.py <repo-root>`。

**なぜ先に並べるか**: 「仕様を作る」ことがタスクに無いと、飛ばしても依頼は片付いたように見える。だから最初に全フェーズを並べ、飛ばすなら理由を書かせる。機械の検査は2段: 書く前(PreToolUse のフックが、実装が進行中の記録なしのコードの書き込みを止める)と、後段(同じ `flow_guard.py` が、終わるとき(Stop フック)・コミットのとき(`--pre-commit`)・CI(`--diff <base>`)に、差分のコードに記録が対応するかを見る)。

## 始める

依頼を受けたら、エージェントの計画機能(plan mode)や設計の案を書くサブエージェント(設計役)で別の計画を作らず、記録を作ってここから始める(PH-19。別の計画は記録と二重になり、設計役の返事を待つ時間と書き直す手間が足される)。計画機能が先に開いていたときは、その計画を記録の要求・不明点・設計に写して続け、同じ調べ物をやり直さない。

1. **記録を作る**: `templates/change.md` → `specs/_changes/YYYY-MM-DD-<name>.md`(id は `python3 scripts/ulid.py`)。進行中の記録が既にあり、同じ依頼の続きなら、それを使う。
2. **規模を振り分ける**(記録の `size`)。差分を一文で言えれば tiny。迷ったら軽い方。レビューや照合で gap が出たら重い方へ上げる。
   - `tiny`: 1〜2ファイルで、要件の意味を変えない(文言の直し、設定値、明らかな不具合の1か所)。不明点・仕様化・設計・タスクは既定で対象外。
   - `bugfix`: 既存の要件どおりに動かない不具合。仕様化と設計は既定で対象外(要件が間違っていたと分かったら full に上げる)。
   - `full`: 新しい振る舞い、要件の追加・変更、2つ以上のケイパビリティにまたがる変更、元に戻しにくい変更。
3. **並べる**: 記録のフェーズの表の7行を埋め(省くものは `対象外: 理由`)、同じ7つを、エージェントのタスクの一覧(Claude Code のタスク、Codex の plan。進み具合を見せるタスクの一覧であって、上で止めた計画機能ではない)にも作る。**要求・実装・照合は省かない。**
4. 進め方は `specs/README.md` のフロントマターの `pace` で決まる(下の「進め方」)。フェーズを終えるたびに表の状態を直す。後のフェーズで前提が崩れたら(要件の変更が要る等)、そのフェーズに戻り、それより後の状態を `未` に戻す。

## 進め方(pace)

- **同時進行**(`pace: concurrent` か、`pace` が無い。リリースしていない間の既定。SF-12): 要求を `済` にしたら、不明点・仕様化・設計・タスク・実装を並べて進めてよい。記録の表は、要求を `済`、不明点から実装まで(対象外にしたものを除く)を `進行中`、照合を `未` にして始める(実装が `進行中` なら門番はコードの書き込みを通す)。仕様の差分(提案)とコードは同じ作業で書き、テストはテスト役(TL-3)が並べて書く。テスト役には、実装を足す前の版を見せる(`git worktree add <一時フォルダ> HEAD` で作った worktree を渡し、作業ツリーの実装を読ませない)。違っていたら人と話して直す(git で戻せるのが前提)。照合は、不明点から実装までが `済` か `対象外` になってから始める。不明点の問い(SF-6)は、答えを待たずに仮定を置いて進め、答えで直す(テストが間違っていると考えたとき(TL-7)などの、止まって人に聞く決まりはそのまま)。
- **順番どおり**(`pace: sequential`、または `concurrent` 以外の値。リリースした(人に配った・公開した)リポで置く。SF-5): 表の順に進める。前のフェーズが `済` か `対象外` になるまで、次を始めない。
- `pace` の値は `concurrent` か `sequential` にする(ほかの値は E35 で、順番どおりになる)。`sequential` から外すときは、spec-change の「変える」で、差分に `- pace: sequential → concurrent(理由)` の行を持ち touches が `[pace]` の決定の記録(人の決定か、錨との照合のある AI 自己採択)を作り、`specs/README.md` の書き換えをその採択と同じコミットに入れる(無いと E36。SF-15)。HEAD の `pace` が順番どおりの値の間は、作業ツリーで書き換えても門番は順番どおりに見る。

**コミットの時機**(同時進行のとき。SF-13):

- 動く単位ができたら、その仕様の採択(`specs: 採択`)、TL-3 でテストを先に置くものは「テスト:」、そして「実装:」のコミットを、この順で続けて作る。守られる要件に触る提案では、採択のコミットより前に「実装:」をコミットしない。
- 「実装:」のコミットは、テストと `check.py` が通る状態でだけ作る(実装の前に落ちることを確かめて置く「テスト:」のコミットはこの外)。テスト全体の走りはその直前に1回(PH-18)。
- 人と話して向きを変える前に、戻れる点を作る。通る状態ならコミットし、通らない途中なら `git stash push -m "<何をしていたか>"` か使い捨てのブランチ(`git switch -c wip/<名前>` でコミット)に退避する。

## フェーズ(手順は phases/ の各ファイル)

| フェーズ | 誰が | 手順 | 成果物 |
|---|---|---|---|
| 要求 | メイン | [phases/elicit.md](phases/elicit.md) | 記録の「要求」 |
| 不明点 | メイン | [phases/elicit.md](phases/elicit.md) | 記録の「不明点と仮定」(人に聞くのは最大3問) |
| 仕様化 | メイン | spec-change スキルの「変える」 | `specs/_proposals/` の提案 → 採択 |
| 設計 | メイン | [phases/plan.md](phases/plan.md) | 記録の「設計」 |
| タスク | メイン | [phases/tasks.md](phases/tasks.md) | 記録の「タスク」の表 |
| 実装 | メイン(テスト役とレビュー役だけサブエージェント。tiny でない変更の重要の指摘は別のレビュー役が確かめる) | [phases/implement.md](phases/implement.md) | コミットと、記録の「レビューの指摘」の表 |
| 照合 | まず `check.py --evidence`、full と埋まらない要件だけ書込なしの検証役、full はセキュリティの回も | [phases/verify.md](phases/verify.md) | 記録の「照合」の表と「確かめた N / M」 |

同時進行のときは、仕様化から実装までの行は並べて進めてよい(上の「進め方」)。要求から実装まではメインの文脈で続ける(前の段の決定の理由を、要約で落とさないため。SF-8)。サブエージェントに渡すのは、読むだけの調べ物(事実を返させる。設計の案は書かせない。PH-19)、実装を見ていないテスト役とレビュー役、full の変更と証拠のスクリプトで埋まらない要件の照合と、full の変更のセキュリティの回だけ。テスト全体(lint・整形の検査を含む)は「実装:」のコミットの直前に1回走らせ、落ちると分かっているテストがあるあいだは走らせない(PH-18。手順は implement.md)。役(テスト役・レビュー役・確かめる回・検証役・セキュリティの役)が走らせるのは、要件を指すテストと関わる束だけで、全体は回させない。依頼には設計の「関わる束」のコマンドを書く(セキュリティの役は差分を読むだけなので除く。PH-20・PH-21)。仕様化で spec-change を呼んでも、計画は変更の記録に持つ(PH-19)。

## 終える

1. 照合で unassessed が0になり、gap に理由と行き先(直した / 提案にした / 人に聞く)が付いたら、記録を `status: done` にする。
2. **軌跡の要約**(OM-14): `python3 scripts/check.py <repo-root> --trail` の最後の行が「要約を出す時」(前回の要約の後に決着した決定記録が7件以上)なら、spec-change の「決める」の手順 1〜3(`skills/spec-change/modes/decide.md`)で軌跡の要約を作る。「まだ出さない」なら作らない。人の返事は求めない。
3. 原則と `gated` の要件に触った AI 自己採択は、人の確認待ちとして要約の先頭(要約を作らないときは報告の末尾)に出す。承認は待たない。確認待ちが3件あるあいだは、原則と `gated` に触る提案を新たに自己採択しない(OM-7)。人が確認したら、spec-change の「決める」の手順 5 で確認の記録を残す。
4. `check.py` をエラー0にしてコミットする(作った要約と確認の記録も同じコミットに入れる)。
5. 報告には、記録のパス、確かめた N / M、残した gap を書き、要約と人の確認待ちがあれば末尾に出す。

途中でやめるときは `status: abandoned` にして理由を書く。
