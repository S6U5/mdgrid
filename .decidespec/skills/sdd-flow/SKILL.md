# 仕様駆動の流れ(sdd-flow)

**動く範囲**: decidespec の形で仕様を持つリポで、コード(`specs/` の外の、Markdown でないファイル)を変える依頼のすべて(頼まれなくても使う)。仕様駆動のツールを何も使っていないリポでは、人が仕様駆動で進めるよう頼んだときだけ、spec-init で specs/ を作ってから使う。他の仕様駆動ツールの仕様を持つリポ(`.specify/`・`.kiro/`・`openspec/` など)では使わず、そのツールのやり方に従う。

パスは道具の根(リポの `.decidespec/`。このファイルから `../../`。spec-init がプラグインからコピーした物で、手で直さない)からの相対: 各フェーズの手順は `skills/sdd-flow/phases/`、記録の雛形は `templates/change.md`、検査は `python3 scripts/check.py <repo-root>`。

**なぜ先に並べるか**: 「仕様を作る」ことがタスクに無いと、飛ばしても依頼は片付いたように見える。だから最初に全フェーズを並べ、飛ばすなら理由を書かせる。機械の検査は2段: 書く前(PreToolUse のフックが、実装が進行中の記録なしのコードの書き込みを止める)と、後段(同じ `flow_guard.py` が、終わるとき(Stop フック)・コミットのとき(`--pre-commit`)・CI(`--diff <base>`)に、差分のコードに記録が対応するかを見る)。

## 始める

1. **記録を作る**: `templates/change.md` → `specs/_changes/YYYY-MM-DD-<name>.md`(id は `python3 scripts/ulid.py`)。進行中の記録が既にあり、同じ依頼の続きなら、それを使う。
2. **規模を振り分ける**(記録の `size`)。差分を一文で言えれば tiny。迷ったら軽い方。レビューや照合で gap が出たら重い方へ上げる。
   - `tiny`: 1〜2ファイルで、要件の意味を変えない(文言の直し、設定値、明らかな不具合の1か所)。不明点・仕様化・設計・タスクは既定で対象外。
   - `bugfix`: 既存の要件どおりに動かない不具合。仕様化と設計は既定で対象外(要件が間違っていたと分かったら full に上げる)。
   - `full`: 新しい振る舞い、要件の追加・変更、2つ以上のケイパビリティにまたがる変更、元に戻しにくい変更。
3. **並べる**: 記録のフェーズの表の7行を埋め(省くものは `対象外: 理由`)、同じ7つを、エージェントのタスクの一覧(Claude Code のタスク、Codex の plan)にも作る。**要求・実装・照合は省かない。**
4. 表の順に進める。前のフェーズが `済` か `対象外` になるまで、次を始めない。フェーズを終えるたびに表の状態を直す。後のフェーズで前提が崩れたら(要件の変更が要る等)、そのフェーズに戻り、それより後の状態を `未` に戻す。

## フェーズ(手順は phases/ の各ファイル)

| フェーズ | 誰が | 手順 | 成果物 |
|---|---|---|---|
| 要求 | メイン | [phases/elicit.md](phases/elicit.md) | 記録の「要求」 |
| 不明点 | メイン | [phases/elicit.md](phases/elicit.md) | 記録の「不明点と仮定」(人に聞くのは最大3問) |
| 仕様化 | メイン | spec-change スキルの「変える」 | `specs/_proposals/` の提案 → 採択 |
| 設計 | メイン | [phases/plan.md](phases/plan.md) | 記録の「設計」 |
| タスク | メイン | [phases/tasks.md](phases/tasks.md) | 記録の「タスク」の表 |
| 実装 | メイン(テスト役とレビュー役だけサブエージェント) | [phases/implement.md](phases/implement.md) | コミット |
| 照合 | まず `check.py --evidence`、full と埋まらない要件だけ書込なしの検証役 | [phases/verify.md](phases/verify.md) | 記録の「照合」の表と「確かめた N / M」 |

要求から実装まではメインの文脈で続ける(前の段の決定の理由を、要約で落とさないため。SF-8)。サブエージェントに渡すのは、読むだけの調べ物、実装を見ていないテスト役とレビュー役、full の変更と証拠のスクリプトで埋まらない要件の照合だけ。

## 終える

1. 照合で unassessed が0になり、gap に理由と行き先(直した / 提案にした / 人に聞く)が付いたら、記録を `status: done` にする。
2. **束を作る**(OM-14): 数えるのは、`specs/_proposals/` の承認待ち(`status: proposed`)のうち OM-13 の対象でないものと、前回の束の後の AI 自己採択(`specs/_decisions/` の `status: accepted` かつ `decided-by: AI` の記録で、どの `specs/_bundles/` の束にもまだパスが載っていないもの。束には載せた記録のパスを並べる)。合わせて1件以上なら、spec-change の「決める」の手順 2〜3(`skills/spec-change/modes/decide.md`)で束を作る。0件なら作らない。`specs/_bundles/` の束と承認の文には、フロントマター(`type: Bundle`、`id`(`python3 scripts/ulid.py`)、`created`)を付ける。
3. OM-13 の対象(守られる要件を消す・弱める提案、承認と照合の仕組みを変える提案)は束に入れず、1件ずつ承認を求める。承認の文(ID と旧・新)を `specs/_bundles/` に保存し(束と同じフロントマター)、指紋(SHA-256 の先頭16文字)を添えて見せる。人の言葉は、ID と承認を示す語(承認・OK・はい など)の両方か、独立した語としての指紋を含む。前の版で8文字の指紋により照合した承認は、そのまま有効。
4. `check.py` をエラー0にしてコミットする(作った束と承認の文も同じコミットに入れる)。
5. 報告には、記録のパス、確かめた N / M、残した gap を書き、束と承認の文があれば末尾に出す。

途中でやめるときは `status: abandoned` にして理由を書く。
