# 要求と不明点

## 要求

依頼を、記録の「要求」に、初めて読む人が分かる文で要約して書く。人の言葉は原文で引用しない(音声入力の誤変換がそのまま残り、公開しうる記録に独り言が出るため)。依頼がどこにあるかは、会話の記録か raw の場所で指す。人の承認も原文で書かず、決定記録の「承認の記録」に要約を書き、会話の記録の場所と指紋で照合する(`check.py --approve <記録> --find <語句>`)。

- 何を変えたいか、なぜか、何ができたら終わりか(受け入れの条件)を書く。受け入れの条件は、確かめられる例を1〜2個(入力 → 期待する結果。境界か失敗時を1つ含める)。例の値は、実際のログ・会話・利用者のデータを写さず、作った値にする(PH-14)。tiny でも省かない。EARS やシナリオへの正式な書き起こしは仕様化でする。
- 関係する既存の要件の ID を `specs/*/spec.md` から探して並べる。無ければ「該当なし」。

## 不明点

要求を実装に落とすときに、答えで結果が変わる問いを洗い出し、次の順で片付ける。

1. **調べる**: コード・`specs/`・資料で分かる事実は、人に聞かずに調べる(読むだけのサブエージェントに渡してよい。渡すのは問いとパスだけ)。調べて候補が複数残ったときだけ、候補と推しを示して聞く。
2. **選ぶ**: 人の好み・範囲・トレードオフのように調べても分からない問いを、影響と不確かさの大きい順(範囲 > 安全・個人の情報 > 使い勝手 > 技術)に並べ、上から選ぶ。人に聞くのは **1つの変更で合計3問まで**(SF-6。3は各ツールの慣習で、根拠のある数ではない)。
3. **聞く**: 1回のメッセージにまとめる。冒頭に「こう理解しました」(要求の要約)と、聞かずに置いた仮定のうち影響の大きいもの(最大3)を載せ、そのあとに問い(選択肢と推し)を並べる。要約の読み違いと仮定の外れを、1回のやり取りで直せるようにする。
4. **書く**: 答えは記録の「不明点と仮定」に「問い → 答え(要約)」で書く。聞かなかったものは「仮定: …(理由)。外れたら: …」と書き、次のフェーズを止めうる仮定には「(止める)」を付ける。
5. **2回目**: 答えや調べ物で前提が崩れたときだけ、合計3問の残りの枠で、もう一度聞いてよい。枠を超えた問いは、仮定として書くか「後回し(理由)」と書く。

聞く問いが無ければ「なし」と書いて `済` にする。実現性が分からないときの試作は、ここで調べ物として、リポの外か捨てるブランチで作る(試作のコードをそのまま実装にしない)。
