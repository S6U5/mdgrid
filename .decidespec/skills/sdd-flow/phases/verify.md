# 照合

実装が仕様どおりかを確かめる。実装した本人は判定しない。

**まずスクリプト**(SF-9): `python3 scripts/check.py <repo-root> --evidence <変更の記録>` を走らせる。要件ごとに、要件を指すテストを今のコードと「前」(記録のパスを件名に含む最初の「テスト:」のコミットの親に、今のテストを重ねたもの)で走らせ、照合の表の行と「確かめた: N / M」を出す。Python 以外・unittest 以外は `--test-cmd "<{file} を含む雛形>"` を渡す。出た行はそのまま記録の「照合」の表に写す。スクリプトが落ち方(アサーションか、要件の手前か)を見分けるのは Python(unittest)と Rust(cargo test)だけで、`--test-cmd` で走らせる言語の行は gap になるので検証役に回す。

**検証役**: 規模が full の変更と、スクリプトで埋まらない要件(unassessed の行: 読んで判定の要件・テストの無い要件と、gap の行)だけ、書込権限のないフレッシュ文脈の検証役に確かめさせる。bugfix と tiny で全部 checked なら、検証役は起動しない。

サブエージェントが使えない環境(Codex の一部など)では、新しいセッションを開いて、そこで同じ依頼を検証役として渡す。同じ文脈で自分で照合したときは、表の上に「自分で照合(フレッシュ文脈でない)」と書く。

検証役に渡すもの: 変更の記録のパス、触った要件 ID の一覧、実装の前後のコミット(実装前は worktree を作って渡す)。渡さないもの: 実装の途中の考え・AI の要約。

検証役(またはスクリプト)が要件ごとに出すもの(記録の「照合」の表):

| 要件 | 結果 | 証拠 |
|---|---|---|
| XX-n | checked | コード: path:line / テスト: file::name / 今: 通った(コマンド) / 前: 落ちた(理由1行) |

- 結果は `checked`(コードの場所・テスト名・今のコードで通った・実装前のコードで落ちた、が揃った)/ `gap`(どれかが欠ける。何が欠けるかを書く)/ `unassessed`(確かめられなかった。理由を書く)のどれか。
- 実装前でも通るテストは要件を確かめていないので `gap`。落ちた理由が引数の形・import など要件の手前なら、落ちたと数えない。
- 証拠は型で書く(`コード: … / テスト: … / 今: … / 前: …`。確かめ方が「読んで判定」の要件は「読んで判定: 何を読んだか」)。型に合わない checked は `check.py` W19。
- 表には、触った要件(タスクの表の要件と、仕様化で変えた要件)を1行ずつ、重複なく並べる。表の下に `確かめた: N / M`(N = checked の数、M = 表の行の数)を書く。

あわせて、実装の前後の差分で、既存のテストの削除・skip・弱体化(アサーションを減らす・緩める)が無いことを確かめ、表の下に1行で書く。指摘は要件と正しさに関わるものに絞る(健全な作業への細かい指摘は、任意の補足に分ける)。

受け取ったら、gap ごとに行き先を決めて書く: 直した(再照合)/ 提案にした(仕様が違っていた)/ 人に聞く。同じ gap の再照合が2回を超えたら、人に聞く。unassessed が残る間は記録を done にしない。`check.py` でエラー0にする(W12 はテストの無い要件)。
