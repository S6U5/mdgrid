# 設計

採択した要件を、どう作るか(how)に落とす。仕様(what)は `specs/` に、設計は記録の「設計」に書く。

設計はメインが書く(SF-7・PH-19)。設計の案を書くサブエージェント(設計役)は使わず、サブエージェントに渡すのは読むだけの調べ物(問いとパスを渡し、事実を返させる)だけにする。エージェントの計画機能(plan mode)が先に開いていたときは、その計画を記録の要求・不明点・設計に写して続け、同じ調べ物をやり直さない(別の計画は記録と二重になり、返事待ちと書き直しの手間が足されるため)。

**まず要るかを決める**: 次のどれにも当たらなければ、設計は `対象外: 条件に当たらない` にする(強いモデルでは、計画は精度をほとんど上げない)。

- 2つ以上のケイパビリティやモジュールにまたがる
- 新しい依存(ライブラリ・サービス)を入れる
- データの形(ファイルの形式・スキーマ・公開のインターフェース)を変える
- 安全・性能・移行が複雑
- 実装の仕方が複数ありえて、選び方で結果が変わる

**書くこと**(記録の1節に収まる量):

- 変える場所(ファイル・モジュール・公開のインターフェース)と、変えない場所。書いたパス・関数・API は、実在を確かめる(`ls`・grep)。
- 中心は「どのパターンを選び、どこへつなぐか」の判断。コードから見えない決定(選ばなかった理由、守るべき制約)を書く。概要の説明は書かない。
- 選んだ案と、却下した案1つ以上を理由つきで。
- 要件 ID ごとに、どこで満たすかを1行で対応させる。対応の無い要件が残ったら、仕様化に戻る。
- 実装で使う検証のコマンドを2段で(PH-21): 「関わる束」(タスクの受け入れのテストと変えた所に関わるテストだけを走らせるコマンド。書いている間(PH-18)と役(PH-20)が使う)と、「全体」(テスト全体に lint・整形の検査と `check.py` を含めたコマンド。「実装:」のコミットの直前と CI が使う)。どちらもテストと検査を走らせるコマンドだけにし、依存の導入・外への送信・git の書き込みを含めない(役はそのコマンドをそのまま走らせる。記録は別のセッションや公開リポの PR で書き換わり得るので、役に写す前に、この行が自分の書いたままかを見る)。
- 長く残る判断(部品の選定・データの形)は、リポの設計の文書(`docs/design.md` 等)にも写す。

**戻る**: 設計の途中で要件の変更が要ると分かったら、仕様化に戻って提案を足し、設計より後のフェーズの状態を `未` に戻す。
