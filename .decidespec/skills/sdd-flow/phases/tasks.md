# タスク

設計を、1つずつ実装してテストが通る大きさのタスクに分け、記録の「タスク」の表に書く。

| # | タスク | 要件 | 完了の条件 | 範囲 | 受け入れ(テスト名) | 状態 |
|---|---|---|---|---|---|---|

- 1タスクは、単独でテストが通る大きさ。コミットは「テスト:」と「実装:」の2つまで(先にテストを置くタスク)か1つ。「テスト:」のコミットは落ちる状態なので、`git bisect` では `git bisect skip` で飛ばす(または `git bisect run` のスクリプトで「テスト:」のコミットに 125 を返す)。
- 「要件」は、そのタスクで満たす要件 ID(`specs/` に実在するもの)。要件に紐づかない作業は「なし(理由)」。
- 「完了の条件」は、観察できる1行(「記録なしでステージすると --pre-commit が 1 を返す」)。
- 「範囲」は、触るファイル・モジュール。範囲をまたぐ作業は、統合のタスクとして分ける。
- 「受け入れ」は、先に書くテストの名前か「読んで判定」。テストを先に置くかは TL-3(振る舞いが先に決まるものとバグ修正は先に、画面の見た目は後で)。
- 並べる順は、テストの準備 → 守られる要件 → その他。依存は番号で書く。並べられるものに印を付けてよいが、実行は1つずつ(同じファイルでの衝突と、暗黙の決定のぶつかりを避ける)。
- 状態は 未 / 進行中 / 済。
