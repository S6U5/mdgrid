# 実装

タスクの表の順に、1タスクずつ進める。実装はメインが行う(SF-8。要求から設計までの判断の理由を持ったまま書くため)。サブエージェントに渡すのは、実装を見ていないテスト役とレビュー役だけ。

**テスト役(サブエージェント)に渡す**(SF-8): 変更の記録のパス・タスクの行・要件 ID・関係するファイルのパス(要件の spec.md と、公開のインターフェースのあるファイル)だけ。テスト役は spec.md の要件と例を自分で読む。メインの考えや要約は渡さない。規約はリポの AGENTS.md / CLAUDE.md にあるので渡さない。fixture は作った値で組むよう添える(実際のログ・会話・利用者のデータを貼らない。実物の形が要るときは形を保って値を置き換える。PH-14)。錠のかかったテストのファイルには書き足さず、新しいファイルに書くよう添える(書き足すと共有部分が変わって E19 になる)。

**メインがすること**:

1. **テストを置く**(TL-3)。振る舞いが先に決まるもの(ライブラリ・CLI・データ処理・書き戻しの規則)とバグ修正は、テスト役が書いた受け入れのテストを実装より先に置き、走らせて落ちることを確かめ、「テスト: [XX-n] …(記録のパス)」でコミットする。画面の見た目や操作感は、作ってから最後に確かめてよい。テストは要件 ID を名前か本文に持つ(`test_TD_4_…` か `[TD-4]`)。
2. **実装する**: テストが通るまで書く。**守られる要件のテストは書き換えない**(`check.py` E19)。テストが間違っていると考えたら止まり、「コード・仕様・テストのどれを直すか」を人に聞く(TL-7)。次のタスクに効く気づき(名前の決め方・環境の落とし穴)は、記録の「実装の気づき」に1行で足す。
3. **レビュー**: 実装を見ていないフレッシュな文脈のレビュー役(書込なし)に、変更の記録のパス・タスクの行・要件 ID・変えたファイルのパスを渡し(差分は `git diff` で自分で読ませる)、要件と正しさの欠けだけを挙げさせる。差し戻しが2回を超えたら人に聞く。
4. **コミット**: 触ったファイルを名指しして stage し(`git add -A` を使わない)、「実装: [XX-n] …」(決定記録のパス)でコミットする。錠は、そのテストを入れるコミットで `check.py --lock` でかける(後のコミットのテストの錠を先に入れない)。人の決定で要件を変えた・消したときだけ、テストを直したコミットで `check.py --lock --relock specs/_decisions/<その記録>` を使う。それ以外で錠の記録を書き換えない(E20)。
5. 記録のタスクの状態を `済` にする。

サブエージェントが使えない環境では、テスト役とレビュー役も新しいセッションで行うか、記録に「独立したテスト役・レビューではない」と書く。全タスクが `済` になったら、実装のフェーズを `済` にして照合へ進む。
